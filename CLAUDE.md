# SLORA project rules

- The brief is `master_prompt.md`; the plan and progress live in `IMPLEMENTATION_PLAN.md` (`P§n` = prompt section, `§n` = plan section). Follow the plan's phases; Phases 0 and 1 are built (entrance, hero, scroll journey with 3D turf, surface-card deck, How we build, chat SHELL) and Phase 2 has started (Sports, and real Contact/About content). The rest of Phase 2 needs real content from SLORA; Phase 3 needs credentials. Only build a section the client actually asked for or that the plan's own phase order calls for next — if they ask for something removed, remove it in full (component, data, tests), don't just unmount it.
- **Never invent** specs, pile heights, areas, certifications, prices, timelines, project claims, or contact details. SLORA's real address (full, with PIN code) and WhatsApp/call number **are** supplied now (`data/contact.ts`, `lib/contact.ts`, `.env.local`) — use those, don't guess beyond them. Unknown = placeholder that is hidden in production.
- **Never lose a lead**: persist first, notify second, channels independent. Never expose lead records to the browser. Keep secrets server-side; only `NEXT_PUBLIC_WHATSAPP_NUMBER` is public and it is read in one place (`lib/whatsapp`).
- Media paths live only in `data/media.ts`. The supplied footage is AI-generated stand-in (`illustrative`), never a specific SLORA project. **CR-1 (2026-09-25) added a second kind of `illustrative`:** real third-party reference photos (`photo/photos_surface/`, converted by `scripts/encode-surface-photos.mjs` — read its header before adding/replacing one, it records exactly which of the client's two supplied photos per surface was used and why, e.g. a watermark or a manufacturer's own branded diagram) — treat these the same as the AI stand-ins (fine to build/review against, not for public launch) but they carry an EXTRA risk the AI footage doesn't: they may be a specific real company's own marketing photography (check the original filename before trusting one), so don't wave through a new one without checking it isn't visibly watermarked, branded, or a diagram/composite rather than a photo.
- Gold (`#D9A441`) is an accent only for text/links/nav (menu items, "CONTACT →", the card-deck name row, chat option chips, dropdown menu items) — those stay muted until hovered/current, on purpose. **Discrete buttons are solid gold by default, not just on hover** (client request 2026-09-22: the chat FAB and other buttons looked "off" until a mouse happened to hover them, which never happens on a touchscreen anyway): the chat FAB, header "BUILD WITH SLORA", `ContactPopover`'s trigger, `InstagramLink`, the card-deck arrows, and the chat panel's close/send/"start again" buttons. Their `:hover` only adds a transform (scale/translateY), never a colour reveal. A secondary button that sits beside an already-gold primary one (About/Contact/HowWeBuild's WhatsApp/Call/Enquire) keeps a lighter, permanent gold tint instead, so the pair keeps a visual hierarchy. The display face is a placeholder behind `--slora-font-display`.
- Commands: `npm run dev|lint|typecheck|test|e2e|assets:check`. Run lint + typecheck + test before calling work done. Read `node_modules/next/dist/docs/` before using an unfamiliar Next 16 API.
- When a phase is finished, update `IMPLEMENTATION_PLAN.md`: tick the phase in section 6 and refresh the plain-English progress report at the top of the file (it must stay readable by non-technical people; report only what was actually verified).
- The chat window is a preview shell (`lib/chat/config.ts`: `CHAT_PREVIEW_MODE`); it must never claim an enquiry was received until it really submits to `/api/leads`.
- The 3D scene must only render while on screen, and heavy code (3D, chat) stays lazy-loaded. E2E runs with 2 workers because 3D is software-rendered on machines without a GPU.
- Scroll-driven footage is **still frames on a canvas, never a scrubbed `<video>`** (a video seeks + decodes on every scroll step and stalls on slow decoders; that was the client's "buffering"). Use `lib/media/frameSequence.ts` with frames from `public/sequences/` (made by `npm run assets:encode`, listed in `data/sequences.ts`). Keep its guard rails: paint at most once per frame, never redraw an identical picture, one draw instead of two when close to a frame, canvas no wider than the frames. More or bigger draws make Chrome block the page on "GPU backpressure" (`FinalizeFrame`), which looks exactly like buffering. The looping hero `<video>` is fine (it just plays).
- Do not add a second layer of smoothing on top of Lenis. Scroll-fade and entrance-fade must live on different elements. Judge smoothness on the PRODUCTION build (`npm run build && npm run start`), not dev, and by measuring (long tasks + frame gaps, and a Chrome trace when something stalls) rather than by eye; real-GPU Edge (`channel: "msedge"`) and software-GL Chromium (the e2e config) behave very differently.
- The surface cards are a deck (`components/cards/CardCarousel.tsx`, data in `data/surfaces.ts`). **Since CR-1 (2026-09-25) the deck is material-based, not sport-based:** 7 cards (Artificial turf, Acrylic, Sports vinyl, Rubber/EPDM, Wooden, Synthetic (PU), Maintenance & resurfacing — the last is a service with no sports row, its whole-card link goes to Contact instead of Sports). Their pictures are illustrative stand-ins, not the sport named on the card; keep the on-screen note. Court cards' slab shows no layer names (court build-ups are unknown). Off-screen cards stay `inert`. Every card has a "Connect with us" button (`lib/cards/enquiry.ts`'s `askAboutCard`, same never-guess rule as Sports below) that opens the chat naming that card; only give a card's `data/surfaces.ts` entry a `video` when real matching footage exists (today: only Artificial turf, reusing `hero-loop`) and a `requirement` when it is an exact `RequirementType` match (today: only Artificial turf → `"Football Turf"`, and the flooring cards → `"Sports Flooring"`) — a near-match still opens the chat, it just doesn't skip the question. Each surface also shows a "PLAYED HERE" row of sport chips (which sport, on this surface) — see the cross-link bullet below; the pairings are marked "to be confirmed by SLORA" on screen (never-invent rule: they're a plausible, self-authored table, not a client-confirmed fact) until `IMPLEMENTATION_PLAN.md` §8 #18 is signed off.
- Projects (`components/sections/Projects.tsx` + lazy `ProjectDetail.tsx`, data in `data/projects.ts`, added 2026-10-12): 5 cards from SLORA's own footage (`video/projects/`, **git-ignored** — 1.5 GB of raw 4K; only the encoded clips in `public/videos/projects/` ship, made by `npm run assets:encode:projects` — read its header before adding a clip, it records which of ~50 clips were kept). Project names come from the delivery folders and `summary` only describes what the clips show; `facts` stays empty until SLORA supplies values with a `source` (never-invent rule; the section says "TO BE CONFIRMED BY SLORA"). The open project is the URL hash (`#projects/<id>`, via `lib/links/crossLink.ts`; use `goToCrossLink`, NOT an `<a href>` — Lenis' anchor handler throws on a `/` in the hash). The detail overlay is z-index 50: above the header (40), below the chat (55) so Enquire can open the chat over it. Real people (some children) appear in the Pickleball clips — confirm permission before launch.
- E2E default port is 3000; if something else holds it, run with `E2E_PORT=<port>` (the config reuses whatever answers on the port, so a different app there makes every test time out).
- Services ("services we provide, step by step", `components/sections/Services.tsx`, data `data/services.ts`, maths `lib/services/scroll.ts`, added 2026-10-12): follows the HowWeBuild video section. Pinned (tall section + sticky stage, ScrollTrigger progress, only opacity/transform per frame, NO extra smoothing) only when wide + `tier === "full"` + not reduced-motion; otherwise four stacked cards. Pictures: `photo/photos_services/` → `npm run assets:encode:services` (paints out the ✦ watermark; the bright planning drawing is darkened). The 4th slide (usage) has no picture yet and reuses the `dusk-court` still. The images contain AI-invented text ("Line-Striper Pro 5000", "Ultra-White Line Paint", "COURT…") — check before launch. Stacking trap: the dark overlay inside `.pictures` is only under the words because `.pictures` has its own `z-index`/`isolation`.
- Chat → WhatsApp (2026-10-12): when the chat's questions are all answered it shows "SEND ON WHATSAPP →", a plain `<a target=_blank>` (a real user click, so no popup blocker) to `wa.me/<number>?text=` with all six answers (`buildWhatsAppUrl(draft)`); SLORA only receives it once the visitor presses Send inside WhatsApp, and the wording says so. The same click also fires `saveLeadQuietly` (`lib/leads/submitClient.ts`): a best-effort `POST /api/leads` with `keepalive` — persist-first where a store exists, silent otherwise, never blocks the WhatsApp step and never makes the chat claim "received" (`CHAT_PREVIEW_MODE` still governs that claim for the no-WhatsApp-number fallback). Verify by intercepting `/api/leads` in a test, not by posting fake leads into the dev store.
- The chat always starts from the NAME (2026-10-12): closing the chat wipes the draft (`ChatPanel`'s second `[open]` effect), so a reopen never skips questions the previous visitor answered, and card/sport buttons pre-fill their requirement just before opening (after that wipe). The "start the conversation" effect must stay safe to run twice on mount: React dev mode runs effects, cleans up and re-runs them, and an earlier `open && !wasOpen.current` guard made the second run do nothing — after the cleanup cleared its timers, the first open showed NO greeting and NO first question. E2E tests must wait for each question before answering (an answer typed while the chat is "typing" is dropped).
- Glassmorphism is reserved for the How We Build panel and the chat window (P§11, 22) — nowhere else, including the header. If a section starts looking see-through/blurred outside those two, that's a bug, not a style choice.
- Device tiers live in `lib/device/capability.ts` (`useCapability()`: `full` = real graphics card, `video` = software rendering, `simple` = data-saver or an explicit `?journey=light`). It has **never** checked screen width — `simple` does not mean "phone". `components/journey/Journey.tsx` (the opening scroll + 3D) is decided by `tier` alone (client request 2026-09-23: match the laptop on a phone too), so it now runs on any phone whose browser reports real WebGL. `components/sections/Sports.tsx`'s sideways rail and `components/sections/HowWeBuild.tsx`'s glass panel still ALSO require `useMediaQuery("(min-width: 900px)")` on top of `tier` — a deliberate, separate width gate, left alone when the journey's was removed; don't assume the two behave the same. **Effects where JavaScript moves big pictures every scroll frame (e.g. the Sports pinned rail) are only for `full`**: on software rendering they stall for up to 1.5 s (measured), while native scrolling (CSS scroll-snap) stays smooth. Avoid reading layout (`clientWidth`, `getBoundingClientRect`, `window.scrollY`) in per-frame code; measure once, or take the scroll value from Lenis.
- Sports (`components/sections/Sports.tsx`, data in `data/sports.ts`): pictures are illustrative stand-ins and the taglines are placeholder wording; `applications`/`technical` only render when verified (with a source); a panel pre-fills the chat only for an exact enquiry-type match (`lib/sports/enquiry.ts`), never a guess. **Since CR-1, 10 panels** (added Badminton, Basketball, Pickleball to the original 7). Each panel shows a "PLAYED ON" row of surface chips, the mirror of the surface cards' "PLAYED HERE" row — both sides read from the one relation table, `data/surfaceSports.ts` (`SPORTS_BY_SURFACE` is hand-written; `SURFACES_BY_SPORT` is derived from it, never edited directly, so the two views can't disagree); a unit test (`surfaceSports.test.ts`) fails if any surface or sport ends up with zero entries on the other side, or an id doesn't exist.
- **Cross-linking a surface card to its sport panel and back** (`lib/links/crossLink.ts`): the URL hash IS the state (`#surfaces/<id>` / `#sports/<id>` — shareable, back-button-friendly, works on a fresh page load too), and the native `hashchange` event is the pub-sub, so there's no separate store to keep in sync. `useCrossLinkTarget(section)` reads it; `goToCrossLink(hash)` sets it (and fires a synthetic `hashchange` when re-clicking a chip for the currently-shown item, since the real event doesn't fire for an unchanged hash). Landing on the target reuses existing scroll machinery rather than duplicating it: in the Sports pinned rail, focusing the target panel's own button triggers the *already-attached* keyboard-focus scroll handler (`Sports.tsx`'s `focusin` listener) for free — this only works because the cross-link effect is declared textually after that listener's `useGSAP` effect (React runs effects in declaration order on mount). `CardCarousel` instead calls `goTo(index)` directly (no such listener exists there) plus `lenis.scrollTo(root, {offset: -96, ...})` — the `-96` compensates for the `position: fixed` header, which otherwise tucks the landed card's top edge underneath it. Both wrap their `setState` call in a named callback (`land()`) invoked from `onComplete`/`requestAnimationFrame`, never called as a bare direct statement in the effect body — `eslint-plugin-react-hooks`'s `set-state-in-effect` rule flags even a one-line indirection like `goTo(x)` sitting directly in a `useEffect`, but not a named callback invoked from a completion handler.
- E2E on this machine (software-drawn graphics, shared with the user): traces are recorded only on retry (recording every test makes the glass chat 2–3× slower); use `--trace on` when debugging a failure. In the pinned Sports rail do NOT use Playwright's `click()` on a panel button (its scroll-into-view moves the row and chases the button): wait for the row to rest and use `page.mouse.click` at the button's position (`pressButton` in `tests/e2e/sports.spec.ts`). Chat tests are `test.slow()` with 30 s assertions.
- The round buttons that hide the ✦ watermark (`lib/media/watermark.ts`'s `cuePosition()`, used by the hero's SCROLL button and `WatermarkCover`) must stay bigger than the mark's own measured size at every frame width, including on a big monitor where the button stops growing (there's a unit test for exactly this: `tests/unit/hero.test.ts`). It was once too small on a large screen and the mark peeked out — if you touch the radius constants, keep that test passing at 4K-sized widths too, not just common ones. It was also, separately, once too BIG: on a narrow/tall phone screen the mark crops off screen entirely, and the phone-fallback branch used to size itself from `maxRadius` (a desktop-appropriate 90 px cap) instead of the screen — a 180 px-wide button, big enough to sit over the hero headline. That fallback is now sized from `Math.min(width, height)`, never from `maxRadius`, and it has its own unit test.
- A value an animation loop sets on an element every frame via `el.style.x = …` (inline style) silently wins over a CSS rule setting the same property on that same element, `!important` or not — a plain specificity trap, easy to forget mid-session. If you need a _static_, breakpoint-only override of a property some `useFrame`/rAF loop also drives (as `three/TurfSurface.tsx`'s `Rig` does to each cross-section label's `transform`/`opacity`), put your override on a wrapping element instead (see `.labelWrap` in `three/turf.module.css`), not on the element the loop touches.
- `ChatPanel` is lazy-loaded once (`ChatWidget.tsx`) and then **stays mounted for the rest of the visit**; it does not remount on a later open. Anything that should happen "each time the chat opens" (the greeting, naming who it's `interest`-ed about via `lib/chat/store.ts`, kicking off the first question) must be an effect keyed on the open-transition (`open && !wasOpen.current`), never a mount-only effect or a `useState` initial value — both silently freeze at the very first open and never update on the next one. `askNext()` is guarded against overlapping calls (a ref, not `typing` state) because the panel's own opening sequence and a fast reply can otherwise both schedule a push and the same question gets asked twice.
- The click-through-container pattern (`Header.module.css`: parent `pointer-events: none`, real buttons `pointer-events: auto`, raised above a sibling's `z-index` when needed) is reused wherever a mostly-decorative absolutely-positioned block sits over a link/button it shouldn't swallow clicks from (e.g. `EditorialCard`'s `.body`/`.connect`). Reach for it instead of re-deriving stacking order from scratch.
- `EditorialCard`'s `.card` has `overflow: hidden`, and its `.word`/`.body` are `position: absolute` — so growing `.body`'s content (e.g. adding a chip row) does **not** grow `.card`'s own box; the card's height comes only from its `min-height`/`max-height`/`aspect-ratio`. Content that gets taller just overlaps whatever else is absolutely positioned in the same box (this is exactly how the CR-1 "PLAYED HERE" chip row visually collided with the giant `.word` behind it, found empirically by measuring `getBoundingClientRect()` gaps across viewport widths, not by eye — same diagnostic method as the watermark-button sizing bug above). If you add content to an absolutely-positioned child of an `overflow: hidden` card, re-check (and likely raise) the card's own `max-height`/`min-height`, don't assume the box will grow to fit.
